Prices: approximate USD before tax; cards exclude the host PC; “est.” means a budget estimate. Speeds: externally reported (M) or estimated (E); model, context and runtime differ. Compute: dense matrix peaks of the GPU, or the NPU where labeled. Apple has no published figure, so its E values are third-party estimates for the matrix units built into each M5 GPU core. Peak compute mostly drives prefill; single-user decode is set by bandwidth, which is why the Macs decode well despite lower peaks. Token time at peak: share of each generated token’s measured time that its memory reads alone would take at peak bandwidth (Memory), and that its arithmetic alone would take at peak vector compute (Compute). The two overlap, so they do not add up; Other is the time neither explains: launches, synchronization, host lookups, slow kernels. High Memory means faster memory helps; high Other means better software helps. Derived from a roofline in the drawer.

One common model score

The shortlist now uses the Artificial Analysis Intelligence Index v4.3.2 throughout. It weights agents 30% (AA-Briefcase v1.1 15%, GDPval-AA v2.1 10%, AutomationBench-AA 5%), coding 20% (Terminal-Bench 4.0 10%, SciCode 10%), scientific reasoning 20% and general capability 30%. This is a broad independent composite, not a pure coding-agent score or a percentage success rate. No ad hoc average of vendor benchmarks is used.

Verified scores: GLM-5.3 Max 45; GLM-5.3-Flash 42; DeepSeek V4.1 Flash Max 39; Qwen3.8-27B Xhigh 34; Qwen3.8-Flash-Next reasoning 40; DeepSeek V4 Flash 0731 Max 34; Qwen3.6-35B-A3B reasoning 18. Hardware sources and precision normalization

Arithmetic units: the main table spans GPU dense peaks and NPU/Neural Engine throughput where labeled: R9700’s dense INT4 matrix peak, NVIDIA FP4/FP8 peaks, Halo’s separate 50-TOPS INT8 NPU, and third-party estimates for Apple’s GPU Neural Accelerators. The Apple values are not rated peaks. These figures do not claim that each recommended runtime executes its quantized weights in that arithmetic; Q4 weight storage does not imply INT4 execution.

Apple compute: GPU Neural Accelerators, not the Neural Engine. Every M5-family GPU core contains a matrix unit that Apple calls a Neural Accelerator. This is the hardware that LLM runtimes such as MLX use through Metal; the 16-core Neural Engine (32-core on Ultra) is a separate, smaller block that most local-LLM runtimes do not use. Apple publishes no FLOPS figure and claims only “over 4×” the peak GPU AI compute of the matching M4 chip (M5, M5 Pro and M5 Max). Microbenchmarks on the A19, whose GPU cores are the same generation, measured about 1,024 FP16 FLOPs (FP32 accumulate) and about 1,900 INT8 ops per core per clock; BF16 was not exposed and FP8/INT4 were not measured. Scaling by core count and an assumed clock (about 1.55 GHz for M5, about 1.75 GHz for Pro/Max/Ultra) gives approximately: M5 10-core 16 TFLOPS FP16 / 30 TOPS INT8; M5 Pro 20-core 36 / 67; M5 Max 40-core 70 / 130 (matching that author’s own M5 Max extrapolation); M5 Ultra 80-core 140 / 260. The M5 figure is consistent with Apple’s 4× claim over a roughly 4 TFLOPS M4 GPU. These are dense FP16/INT8 peaks, not FP4: NVIDIA’s headline FP4 numbers are not like-for-like. The only direct M5 Max matmul measurement found, about 19.9 TFLOPS FP16, is described by its author as directional and sits well below the derived peak, so treat the table values as ceilings. Why the Macs still decode well: single-user decode streams the active weights once per token, so it is limited by memory bandwidth (614 GB/s on M5 Max, 1.2 TB/s on M5 Ultra) and by fitting the model in unified memory, not by peak compute. Compute shows up in prefill: M5 Max prefills Flash-Next at about 1,100 tok/s (B1) against about 12,000 tok/s on an RTX PRO 6000 (B9), which is the practical cost of lower matrix throughput. For reference, the Neural Engine is about 40 TOPS on 16 cores (extrapolated from M4’s 38 TOPS; not an official M5 figure).

  1. H1 · Apple laptops. Apple technical specifications: M5 153 GB/s / 32 GB max, M5 Pro 307 / 64, full M5 Max 614 / 128. The 32-core M5 Max has only 460 GB/s. Apple’s GPU developer talk confirms neural accelerators and INT4/INT8 tensor APIs, but supplies no comparable absolute dense FP4/FP8 GPU peak. An unpublished value is not zero performance.
  2. H2 · AMD unified-memory systems. Ryzen AI Halo specifications; Max+ 395 specifications. 128 GB, 256-bit LPDDR5X-8000 = 256 GB/s. OEM settings affect GPU allocation; faster-memory variants can differ. The separate 50-TOPS NPU is INT8 and is not the accelerator used for most of these LLM measurements.
  3. H3 · RTX 4090. NVIDIA product specifications and Ada announcement: 24 GB, 1,008 GB/s, ~1,321 sparse FP8 TFLOPS, divided by two for ~661 dense. Quantized 4-bit weights can run without native FP4 arithmetic.
  4. H4 · R9700. AMD specifications (32 GB / 640 GB/s), Sapphire precision brochure, p. 1: explicitly “FP8 Matrix Dense — 383 TFLOPS” and “INT4 Matrix Dense — 766 TOPS.” INT4 operations are not floating-point operations.
  5. H5 · RTX 5090. Product page; NVIDIA Blackwell architecture whitepaper: dense / sparse FP4 1,676 / 3,352 TFLOPS. Dense FP8 is half dense FP4 (838). 32 GB, 1,792 GB/s.
  6. H6 · RTX PRO 6000. NVIDIA PRO architecture whitepaper, pp. 45–47: Workstation FP4 2,015.2 / 4,030.4 TFLOPS and FP8 1,007.6 / 2,015.2 (dense / sparse). 96 GB ECC, 1,792 GB/s. The 300 W Max-Q has different compute; the two-card row sums full-power Workstation-class peaks and does not imply linear inference scaling.
  7. H7 · Spark. NVIDIA specs and PNY’s explicit footnote, “Theoretical FP4 TOPS performance using sparsity feature.” 1,000 sparse TFLOPS / 2 = 500 dense FP4; FP8 is half-rate, 250. This is a theoretical normalization, not measured GEMM. Two Sparks require sharding and communication; 256 GB is not one bus at 546 GB/s.
  8. H8 · Mac Studio. Apple specs list 96/256/512 GB M5 Ultra, 1.2 TB/s. 21 September review explicitly says 512 GB is due late October. All direct M5 Ultra measurements cited here used 256 GB. M5 Max Studio has the same stated 614 GB/s maximum as the full Max laptop; thermals and runtime can change speed.
  9. H9 · DGX Station. Current NVIDIA datasheet, p. 3: 252 GB HBM3e at 7.1 TB/s plus 496 GB LPDDR5X at 396 GB/s; 900 GB/s NVLink-C2C, 1,600 W system / 20 A circuit. FP4 reads “20 | 15³ PFLOPS”; footnote 3 is “Without sparsity.” Thus 15 PFLOPS is the explicitly specified dense FP4, not 10 derived from a generic halving rule. FP8’s 10 PFLOPS is sparse; dense 5 PFLOPS is derived. This shipping/OEM spec supersedes the earlier 784 GB / 8 TB/s announcement. Optional RTX graphics is not counted.

Roofline: what limits single-user decode

Why a roofline: a device can deliver at most min(bandwidth ÷ bytes per token, compute peak ÷ operations per token) tokens per second. The bytes and operations come from each model’s configuration and the deployed precision; the peaks come from spec sheets. That gives a ceiling for every pairing with no measured input. The measured speed divided by that ceiling is its attainment. All inputs, formulas and outputs are generated by scripts/roofline.py into data/roofline.json, and the validator checks that every number here and in the hardware map matches.

Per emitted token: weights streamed are the active parameters at the deployed precision. Cache reads are added for the attended context; Flash-Next and the GLM models attend to at most 2,048 selected tokens, Qwen models to the full context. Operations are 2 per active parameter, plus ~3 per weight read for unpacking 4-bit weights, plus attention (4 × layers × heads × head dim × attended tokens). With drafting (k drafted tokens per step, a emitted), every drafted token is computed, so operations scale by (k+1)/a. A dense model reads its weights once per step. A sparse MoE’s drafted tokens hit partly different experts; a step is assumed to read 1 + 0.25k times the single-token weights. The two-Spark GLM-5.3-Flash run caps this at 4.6× for k=7 (B16). The compute ceiling is the GPU’s vector FP32 peak, not the tensor/matrix peak: one token at a time is a matrix-vector product that tensor units cannot run efficiently, and the lower ceiling never understates compute. Prompt processing reads each weight once per chunk of ~2,048 tokens, so it is measured against the matrix FP16 peak instead.

Reading it: every decode pairing has arithmetic intensity (operations per byte) below its device’s ridge point, so on peak figures memory always takes longer than compute. The hardware map turns this into a time budget per token. Memory is the share of the measured time the weight and cache reads alone would take at peak bandwidth: 15–94% here. Compute is the share the arithmetic alone would take at peak vector compute: 2–48%, highest on the Macs, whose vector units are modest, and on drafted models, which compute several tokens per weight read. A GPU overlaps the two, so they do not add; Other is 100% minus the larger, the time neither explains: kernel launches, synchronization, host-memory lookups and kernels too small to fill the chip. Where Memory is high (RTX 4090 83–85%), faster memory moves the result. Where Other is high (RTX PRO 6000 83–85%), better software moves it: graph capture, fused kernels, drafting. Where Compute comes within ~2× of Memory (the Macs with drafting), real kernels may make compute the practical limit, because they rarely reach peak. Prompt processing sits on the other side of the ridge, compute-bound at 16–45% of matrix peak. That is where lower Apple compute shows up, as time to first token.

How the estimates were made

Decode scope: one active request, warm model, short prompts; the remaining analytical scenarios target roughly 2–8K. Four rows remain estimates: M5 Pro, dual PRO, M5 Ultra 512 GB and Station. M5 Pro spans fresh coding through favorable repetitive editing. Measured rows retain their stated contexts and drafting settings: M5 Max, Spark, Halo, R9700, dual Spark and M5 Ultra 256 GB include MTP or DFlash2 drafting; RTX 4090, RTX 5090 and the single-PRO headline do not. The separate memory comparison budgets 128K context. The M5 Ultra 512 GB and Station estimates assume DFlash2 drafting; the dual-PRO estimate adds no speculative multiplier. Ranges are planning scenarios, not statistical confidence intervals.

  • M5 Pro with drafting: Qwen3.8-27B MTPLX Optimized Speed (dynamic Q4, 20.4 GB weights), native MTP head, tuned draft depth 1–3, single stream, approximately 2–8K prompt, thinking off or medium reasoning. MTPLX reports 52.6 tok/s on M5 Max at 4,061 prompt tokens / 512 output; its model card reports 58.7 tok/s on a fresh medium-reasoning coding task, official sampling temperature 1.0 / top-p .95 / top-k 20. Both already include MTP; no extra speculative multiplier is applied.
  • Cross-laptop extrapolation: take an M5 Max MTPLX reference at 614 GB/s, multiply by the laptop’s bandwidth ratio and a scenario factor of 0.8–1.0 for verification, runtime and thermal differences: speed ≈ reference × (bandwidth / 614) × 0.8…1.0. On M5 Pro (307 GB/s) the fresh-coding references 52.6–58.7 give 21.0–29.4 and the 87.6 repetitive-editing reference gives 35.0–43.8; the headline 21–44 spans both (see M5 Pro). On base M5 (153 GB/s) Qwen3.8-27B scales to only 10.5–14.6 fresh and ~22 editing, so the base M5 row uses the measured small MoE instead. Verification compute need not scale with bandwidth, so real results can fall outside these ranges.
  • Draft acceptance and fit: the model-card coding run reports acceptance by depth of .95 / .88 / .80 and a 50–53 ms verifier round on M5 Max. The estimates assume similarly favorable coding, not guaranteed acceptance on arbitrary tasks. MTPLX uses the model’s own head, not a second full draft model; its catalog reports roughly 25 GiB serving peak for this pack, so 32 GB needs a light application load and short context. Tune depth on the target Mac. Long xhigh reasoning was only 35.1–37.3 tok/s on M5 Max in the same card and is outside this faster planning scenario.
  • Qwen27 Q4 without drafting (reference): approximate streamed weight payload 16 GB. Use 60–80% of advertised bandwidth: tokens/s ≈ bandwidth_GBps × 0.60…0.80 / 16. Rounded: M5 6–8; M5 Pro 12–16; RTX 4090 38–50; R9700 24–32. No headline uses this formula any more: the 4090 (B10) and R9700 (B8) are now measured. Check: the 4090’s measured 46.2 tok/s at 4K sits inside its 38–50 forecast, while the RTX 5090’s 59 tok/s (B3, LM Studio on Windows) implies only ~53% bandwidth utilization, so runtime choice moves real results by more than the formula’s utilization band.
  • RTX PRO 6000, previous Qwen27 Q8 alternative: ~29.4 GB payload at 58–80% bandwidth gives ~35–49 tok/s. Retained as an alternative, not the capability-first headline pairing.
  • M5 Ultra 512 GB → GLM-5.3, 20–40 tok/s with drafting, conditional estimate. The 512 GB model has the same chip and 1.2 TB/s as the 256 GB model; its extra capacity is what lets it run GLM-5.3 (365.3 GB IQ4_XS, or a ~420 GB oQ4-class MLX build). Without drafting: ~40B active parameters × ~0.60 bytes ≈ 24 GB per token; 1,200 GB/s × 30–50% effective utilization / 24 ≈ 15–25 tok/s, which fails the gate. Cross-check: GLM-5.2 oQ4 on a 512 GB M3 Ultra measured 14.5 tok/s, or ~21 scaled to 1.2 TB/s. With drafting, apply the smallest measured DFlash2 gain on a GLM MoE in oMLX (B17: 1.34× at a 4K prompt to 1.61× at 200 tokens): 20.1–40.2, displayed as 20–40. A DFlash2 drafter for GLM-5.3 exists (B18), and oMLX has merged DFlash2 for GLM-5.3-Flash, but no full GLM-5.3 run on a Mac was found. The configuration ships late October. Low confidence.
  • DGX Station / GLM-5.3 IQ4_XS: 21–40 tok/s with drafting, conditional estimate. Start with 365.3 GB weights and 252 GB HBM; reserve 24–40 GB HBM for runtime, cache and verification buffers. Approximately 212–228 GB weights stay in HBM and 137–153 GB in CPU memory. Assume balanced expert placement makes the CPU-served share of active-weight traffic about 38–42%, rather than treating all 748 GB as HBM.
  • Station bandwidth calculation: use the same approximate 24 GB active-weight traffic per token as the Ultra estimate. At CPU fraction x, effective bandwidth fraction u, and non-weight overhead h, t ≈ 24×(1−x)/(7100×u) + 24×x/(396×u) + h seconds/token. With x=.38–.42, u=.50–.70 and h=.004–.008 s, this gives 15.9–25.1 tok/s without drafting. The 40% of traffic served from CPU memory takes about 90% of the time. The 900 GB/s NVLink-C2C link does not eliminate the slower 396 GB/s CPU-memory supply; bandwidths are not added.
  • Station drafting assumption: the earlier 1.4–1.8× gain was a free assumption. It is now replaced by the smallest measured DFlash2 gain on a GLM MoE, 1.34–1.61× (B17, oMLX on M5 Ultra), giving 21.3–40.3 tok/s, displayed as 21–40. The smallest gain is used because split memory makes the Station bandwidth-bound: on overhead-bound systems the same drafter gains far more (2.2–3.4× for GLM-5.3 on four GB300s, B18; 2.6–3.5× for GLM-5.3-Flash on two Sparks, B16). Drafting helps a bandwidth-bound MoE only through expert reuse across drafted tokens; see the roofline. Requires the GLM-5.3 DFlash2 drafter and an optimized split-memory backend for the exact quantization. Without working drafting, the 16–25 baseline fails the gate and GLM-5.3-Flash in HBM (B15, ~137 tok/s) is the fallback. Confidence is low.
  • Station alternatives: MiMo-V2.6-Pro scores 46, above GLM-5.3, and is MIT-licensed, but its 1.0T / 42B-active MXFP4 checkpoint is ~566 GB. On Station 338–354 GB of it would sit in CPU memory (CPU traffic share x=.60–.63). With ~23 GB active-weight traffic per token, the same u, h and drafting gain give 16–29 tok/s; it fails the gate. No measured local result was found. GLM-5.3-Flash on Station fits entirely in HBM and is measured at ~137 tok/s without speculation, 206 with MTP and 305–470 with DFlash2 (B15): the fast alternative if score 42 is enough.

RTX PRO: roofline plus measured latency anchor

Verified anchor: Kubesimplify reports 81.45 tok/s on two RTX PRO 6000s with Flash-Next FP8, tensor parallelism 2, one request, 1,024 input / 512 output tokens, no MTP. Four cards achieved only 64.61 tok/s. This is direct evidence against scaling decode from summed peak bandwidth alone. Single-card FP8 did not fit. A single-card NVFP4 measurement now exists (B9) and checks the forecast below. There is still no dual-card GLM-5.3-Flash measurement; four cards are measured at 63.7 tok/s (B13).

  • Compute and bandwidth roofs: R ≤ min(F / C, B / D), where F is FLOP/s, C FLOP/token, B bytes/s and D bytes/token. PRO/Spark ratios are 2,015/500 ≈4.0× FP4 compute and 1,792/273 ≈6.6× bandwidth. Flash-Next’s ~6B active backbone gives a lower-bound ~12 GFLOP/token; PRO’s ideal compute roof is ~168,000 tok/s, versus only 224–448 tok/s for 4–8 GB traffic/token. Arithmetic intensity is ~1.5–3 FLOP/byte versus a ~1,124 FLOP/byte hardware ridge point: strongly bandwidth-side. For dual-PRO GLM Flash, ~36 GFLOP/token and 10.8–13 GB traffic give a nominal bandwidth roof ~276–332 tok/s versus ~112,000 compute-roof tok/s. IQ4_XS is not native FP4 tensor math; that compute roof is only a generous bound, not attainable kernel throughput. Batch-one small GEMVs, dequantization and launches can dominate despite enormous peak FLOPS.
  • Latency model: t ≈ max(C/F_effective, D/(B×u)) + h, with effective streaming utilization u and remaining per-token overhead h. Attention traffic, routing, quantization, launch gaps, sampling, lookup staging and collectives matter. Use short-context single-stream operation with warm lookup caches; no bulk weight paging. The 81.45 tok/s FP8 anchor is 12.28 ms/token. Assuming 6–10 GB FP8 traffic and 60% aggregate streaming utilization consumes 2.79–4.65 ms in weight reads, leaving 7.63–9.49 ms residual overhead. This calibrates the order of magnitude, but one observation cannot identify traffic, utilization and overhead separately. Four cards at 15.48 ms/token reinforce the communication/launch floor.

  • Drafting and Spark cross-check: Spark’s 36.83–45.75 tok/s already includes MTP3, so multiplying it by 6.6 would mix memory scaling with verification and acceptance effects. Common basis: 131,072 total cached tokens (prompt plus generated output), one active request, no extra prefix-cache copies or concurrent sessions. All displayed memory is decimal GB (10⁹ bytes), including converted GiB sources. Resident memory means weights plus persistent attention/recurrent/MTP state; SSD lookup tables are listed separately. Runtime allowances are planning reserves for scratch buffers, graph/workspace and allocator overhead, not measured peaks. Add roughly 6–10 GB for the OS and applications on unified-memory machines. Chunked prefill is assumed; unchunked long-prompt processing can require much more memory.

  • Qwen3.8-27B: official config has 16 full-attention layers, 4 KV heads and 256-dimensional heads. With 16-bit K/V: 131072 × 16 × 2 × 4 × 256 × 2 = 8.59 GB. Allow one full-attention MTP layer (~0.54 GB) plus 48 FP32 recurrent states (~0.15 GB) → ~9.3 GB. With 20.4 GB dynamic-Q4 weights, resident total is ~30 GB; add 4–8 GB runtime. Thus the earlier 32 GB laptop fit is for short context, not this 128K budget. Cache quantization can reduce demand if the chosen runtime supports it.
  • Flash-Next: official config has 12 full-attention layers, 2 KV heads, dimension 256, plus one MTP attention layer. Their 16-bit KV is ~3.49 GB. Add ~0.10 GB sparse-indexer keys (4× compression) and ~0.11 GB FP32 recurrent state → ~3.7 GB, rounded to 4. The selected MTPLX pack keeps ~83 GB weights resident and ~32 GB lookup tables on SSD: ~87 GB resident before 4–8 GB runtime. Different NVFP4 or all-resident packs have different weight budgets.
  • GLM-5.3: official config has 78 layers, MLA latent rank 512 and rotary key dimension 64. With one MTP layer and compressed 16-bit latent cache: 131072 × 79 × (512+64) × 2 ≈ 11.93 GB. Budget ~0.74 GB for 22 sparse-indexer key sets → ~12.7 GB, rounded to 13. IQ4_XS weights 365.3 GB + cache ≈378 GB; runtime reserve 8–16 GB. This assumes a backend that stores compressed MLA, not expanded per-head K/V.
  • GLM-5.3-Flash: official config has 11 sparse-attention layers with latent rank 512 and no rotary-key component, plus 34 recurrent layers. Budget one extra MLA layer for MTP: ~1.61 GB latent KV, ~0.10 GB 4×-pooled indexer keys and ~0.14 GB FP32 recurrent state → ~1.85 GB, rounded to 2. Depending on Q4 artifact, 156.82–199.71 GB weights + cache ≈159–202 GB; runtime reserve 8–16 GB. Backend distinction matters: expanded 64-head K/V instead of compressed MLA can consume ~95 GB for the 11 attention layers alone (~103 GB including one MTP layer), making the 128K fit much larger. The table is the compressed-cache scenario, not a claim that every oMLX/GGUF backend uses it.
  • DeepSeek V4 Flash 0731: 0731 config uses 21 attention layers compressed 4× and 20 compressed 128×, 512-dimensional shared KV, 128-dimensional index keys and a 128-token local window. Following the reference implementation’s BF16 cache layout, main compressed KV plus index keys and local windows total ~0.91 GB at 128K; reserve ~1 GB including small compressor state. About 155.1 GB Q4 weights + cache ≈156 GB; add 8–16 GB runtime. Three 0731 draft layers add small local windows, not three full context copies.

35 tok/s selection and ordering

Eligibility requires a measured value or range upper bound ≥35 tok/s, not a midpoint ≥35 and not a guaranteed floor. Choose the highest-scoring eligible model, then order devices by AA score and decode midpoint ascending. The speed gate uses each row’s stated short-context measurement/scenario; the separate 128K memory budget does not imply that speed at 128K. Halo (32–47), dual Spark (28–63), M5 Ultra 512 GB (20–40) and Station (21–40) qualify despite lower endpoints below 35. The two GLM-5.3 rows qualify only with an assumed DFlash2 drafter; without it both fall to 15–25 and the next pairing is GLM-5.3-Flash. MiMo-V2.6-Pro (46) fails on Station (16–29). Extra capacity buys headroom, not automatically more decode speed. Scores describe evaluated model settings, not verified local quantization quality.

Parameter counts and architecture

B = billion parameters; active = per-token backbone work, not resident memory. Dense Qwen27 uses essentially its whole language backbone; MoE models select experts, but all resident experts still consume memory. GLM-5.3: 753B / 40B active; GLM Flash: 320B / 18B; DeepSeek V4 Flash: 284B / 13B; Qwen3.8-27B: 27B dense; Qwen3.6-35B-A3B: 35B / 3B. Counts follow vendor conventions and do not always separately itemize vision or draft heads. Flash-Next’s ~180B sum is 125B backbone +51B lookup embeddings +4B MTP, with 6B active backbone. DeepSeek V4.1’s ~763B full checkpoint includes a 552B backbone and 196B Engram tables plus auxiliary components; 16B active is decode (prefill: 8B). Sparse table lookups and draft verification are additional work, so these active counts alone are not FLOP or bandwidth budgets. The cloud models’ parameter counts and Dense/MoE architecture are undisclosed.

Artificial Analysis’s current open-weight index ranks MiMo-V2.6-Pro (46), GLM-5.3 (45), Kimi K3 (44), then GLM-5.3-Flash (42) in broad intelligence. Rack GPUs (B200/B300/MI350) require server infrastructure and are outside this desk/laptop brief; DGX Station is the enterprise upper bound.

Devices not yet in the map: the Ryzen AI Max+ PRO 495 with 192 GB LPDDR5X-8533 (273 GB/s, up to 160 GB usable by the GPU, $6,399–9,249 across vendors, first systems ship November 2026) has no independent LLM measurements yet. Purchase takeaway: For one practical machine today, the M5 Ultra 256 GB has strong measured large-model options; M5 Max 128 GB is the portable alternative; Spark is attractive for CUDA development, and a second Spark unlocks GLM-5.3-Flash at 28–63 tok/s with DFlash2. Halo now runs the same score-40 model as Spark at similar measured speed for less money. A single RTX PRO 6000 is the fastest measured score-40 setup if the host has ample RAM. An RTX 5090 is a responsive compact-model accelerator, not a replacement for a 256 GB memory pool. The best end-to-end agent is the one that completes the task correctly with fewer retries—not necessarily the highest decode number.
