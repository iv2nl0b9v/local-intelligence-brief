One common model score

The shortlist now uses the Artificial Analysis Intelligence Index v4.3.2 throughout. It weights agents 30% (AA-Briefcase v1.1 15%, GDPval-AA v2.1 10%, AutomationBench-AA 5%), coding 20% (Terminal-Bench 4.0 10%, SciCode 10%), scientific reasoning 20% and general capability 30%. This is a broad independent composite, not a pure coding-agent score or a percentage success rate. No ad hoc average of vendor benchmarks is used.

Verified scores: GLM-5.3 Max 45; GLM-5.3-Flash 42; DeepSeek V4.1 Flash Max 39; Qwen3.8-27B Xhigh 34; Qwen3.8-Flash-Next reasoning 40; DeepSeek V4 Flash 0731 Max 34; Qwen3.6-35B-A3B reasoning 18. Use the stated reasoning configurations: this is a shared evaluation methodology, not an equal-compute comparison. Scores do not establish quality retention in any local quantization. The 0731 text model is distinct from its vision variant.

The AA Coding Agent Index v1.5 is more coding-specific (DeepSWE v1.1, Terminal-Bench 4.0 and SWE-Atlas-QnA), but complete public results for all seven local models could not be verified. Vendor-specific results below remain background evidence and are no longer mixed in the visible comparison.

Hardware sources and precision normalization

Arithmetic units: Mac rows select the numerically higher dense INT8 GPU estimate instead of the FP16 estimate; other GPU rows show floating-point throughput. Precision is labelled in every row, and a higher INT8 number does not imply faster floating-point inference. Figures are dense hardware peaks or estimates (E), with no credit for skipped zero operations or structured sparsity; different precisions are not directly comparable. Halo shows a mixed-operation sum of the separate GPU and NPU ratings: 60 FP16 TFLOPS + 50 INT8 TOPS = 110 trillion operations/s. These engines can work concurrently, but simultaneous peak rates are not verified and share power and memory. This aggregate is neither 110 TFLOPS nor an INT8-only rating, and the cited llama.cpp decode run uses the GPU, not the NPU. CPU compute is excluded. Apple Neural Engine compute is omitted because no verified dense rating for these configurations is available. Apple INT8 TOPS are GPU matrix-unit estimates, not Neural Engine ratings: adding them to FP16 matrix TFLOPS would double-count the same accelerator. A GPU + Neural Engine aggregate would require an independently sourced dense Neural Engine rate and concurrent execution support; Apple describes using both in Metal upscaling, but that supplies no numeric dense peak or evidence of combined throughput in these LLM runs. Two-device rows sum the same floating-point metric across devices; this does not predict inference scaling. Quantized weight storage does not establish execution precision.

Apple compute: GPU Neural Accelerators, not the Neural Engine. Every M5-family GPU core contains a matrix unit that Apple calls a Neural Accelerator. This is the hardware that LLM runtimes such as MLX use through Metal; the 16-core Neural Engine (32-core on Ultra) is a separate, smaller block that most local-LLM runtimes do not use. Apple publishes no FLOPS figure and claims only “over 4×” the peak GPU AI compute of the matching M4 chip (M5, M5 Pro and M5 Max). Microbenchmarks on the A19, whose GPU cores are the same generation, measured about 1,024 FP16 FLOPs and about 1,900 INT8 operations per GPU core per clock (FP32 and INT32 accumulation respectively); BF16 was not exposed and FP8/INT4 were not measured. Scaling by core count and an assumed clock (about 1.55 GHz for M5, about 1.75 GHz for Pro/Max/Ultra) gives approximately: M5 10-core 16 TFLOPS FP16 / 30 TOPS INT8; M5 Pro 20-core 36 / 67; M5 Max 40-core 70 / 130 (matching that author’s own M5 Max extrapolation); M5 Ultra 80-core 140 / 260. The table selects the higher INT8 estimate; it does not sum the two modes or establish the precision used by the decode benchmark. The M5 figure is consistent with Apple’s 4× claim over a roughly 4 TFLOPS M4 GPU. These are dense FP16/INT8 estimates, not FP4: NVIDIA’s headline FP4 numbers are not like-for-like. The only direct M5 Max matmul measurement found, about 19.9 TFLOPS FP16, is described by its author as directional and sits well below the derived peak, so treat the table values as ceilings. Why the Macs still decode well: single-user decode streams the active weights once per token, so it is limited by memory bandwidth (614 GB/s on M5 Max, 1.2 TB/s on M5 Ultra) and by fitting the model in unified memory, not by peak compute. Compute shows up in prefill: M5 Max prefills Flash-Next at about 1,100 tok/s (B1) against about 12,000 tok/s on an RTX PRO 6000 (B9), which is the practical cost of lower matrix throughput.

  1. H1 · Apple laptops. Apple technical specifications: M5 153 GB/s / 32 GB max, M5 Pro 307 / 64, full M5 Max 614 / 128. The 32-core M5 Max has only 460 GB/s. Apple’s GPU developer talk confirms neural accelerators and INT4/INT8 tensor APIs, but supplies no comparable absolute dense FP4/FP8 GPU peak. An unpublished value is not zero performance.
  2. H2 · AMD unified-memory systems. Ryzen AI Halo specifications; Max+ 395 specifications. 128 GB, 256-bit LPDDR5X-8000 = 256 GB/s. OEM settings affect GPU allocation; faster-memory variants can differ. The Halo platform specifications publish up to 60 FP16 TFLOPS and 50 NPU TOPS (INT8). The AMD Halo architecture whitepaper describes feeding the GPU, CPU and NPU simultaneously. We sum only the GPU and NPU ratings, 60 + 50 = 110 trillion mixed operations/s; simultaneous peaks have not been demonstrated here. The previous nominal FP32 estimate has been replaced by the published FP16 rate. The NPU is not used in the cited llama.cpp decode measurement. Dense INT8 matrix throughput is supported by the XDNA2 GEMM architecture study; no sparsity multiplier is applied to either component.
  3. H3 · RTX 4090. NVIDIA product specifications and Ada announcement: 24 GB, 1,008 GB/s, ~1,321 sparse FP8 TFLOPS, divided by two for ~661 dense. Quantized 4-bit weights can run without native FP4 arithmetic.
  4. H4 · R9700. AMD specifications (32 GB / 640 GB/s), Sapphire precision brochure, p. 1: explicitly “FP8 Matrix Dense — 383 TFLOPS”.
  5. H5 · RTX 5090. Product page; NVIDIA Blackwell architecture whitepaper: dense / sparse FP4 1,676 / 3,352 TFLOPS. Dense FP8 is half dense FP4 (838). 32 GB, 1,792 GB/s.
  6. H6 · RTX PRO 6000. NVIDIA PRO architecture whitepaper, pp. 45–47: Workstation FP4 2,015.2 / 4,030.4 TFLOPS and FP8 1,007.6 / 2,015.2 (dense / sparse). 96 GB ECC, 1,792 GB/s. The Workstation datasheet specifies PCIe 5.0 ×16. Its per-direction encoded-data ceiling is 32 GT/s × 16 lanes × 128/130 ÷ 8 = 63.0 GB/s before packet overhead. The dual-card row assumes full-width slots: this is a link ceiling, not measured GPU-to-GPU throughput; host routing, lane allocation, peer access and staging can reduce it. The 300 W Max-Q has different compute; the two-card row sums full-power Workstation-class peaks and does not imply linear inference scaling.
  7. H7 · Spark. NVIDIA specs and PNY’s explicit footnote, “Theoretical FP4 TOPS performance using sparsity feature.” 1,000 sparse TFLOPS / 2 = 500 dense FP4; FP8 is half-rate, 250. This is a theoretical normalization, not measured GEMM. The NVIDIA two-Spark guide specifies a 200 Gb/s direct link: 200 ÷ 8 = 25 GB/s per direction before protocol overhead. This is separate from each node’s memory bandwidth. Two Sparks require sharding and communication; 256 GB is not one bus at 546 GB/s.
  8. H8 · Mac Studio. Apple specs list 96/256/512 GB M5 Ultra, 1.2 TB/s. 21 September review explicitly says 512 GB is due late October. All direct M5 Ultra measurements cited here used 256 GB. M5 Max Studio has the same stated 614 GB/s maximum as the full Max laptop; thermals and runtime can change speed.
  9. H9 · DGX Station. Current NVIDIA datasheet, p. 3: 252 GB HBM3e at 7.1 TB/s plus 496 GB LPDDR5X at 396 GB/s; 900 GB/s NVLink-C2C, 1,600 W system / 20 A circuit. FP4 reads “20 | 15³ PFLOPS”; footnote 3 is “Without sparsity.” Thus 15 PFLOPS is the explicitly specified dense FP4, not 10 derived from a generic halving rule. FP8’s 10 PFLOPS is sparse; dense 5 PFLOPS is derived. This shipping/OEM spec supersedes the earlier 784 GB / 8 TB/s announcement. Optional RTX graphics is not counted.

How the estimates were made

Decode scope: one active request, warm model, short prompts; the remaining analytical scenarios target roughly 2–8K. Four rows remain estimates: M5 Pro, dual PRO, M5 Ultra 512 GB and Station. M5 Pro spans fresh coding through favorable repetitive editing. Measured rows retain their stated contexts and drafting settings: M5 Max, Spark, Halo, R9700, dual Spark and M5 Ultra 256 GB include MTP or DFlash2 drafting; RTX 4090, RTX 5090 and the single-PRO headline do not. The separate memory comparison budgets 128K context. The M5 Ultra 512 GB and Station estimates assume DFlash2 drafting; the dual-PRO estimate adds no speculative multiplier. Ranges are planning scenarios, not statistical confidence intervals.

  • M5 Pro with drafting: Qwen3.8-27B MTPLX Optimized Speed (dynamic Q4, 20.4 GB weights), native MTP head, tuned draft depth 1–3, single stream, approximately 2–8K prompt, thinking off or medium reasoning. MTPLX reports 52.6 tok/s on M5 Max at 4,061 prompt tokens / 512 output; its model card reports 58.7 tok/s on a fresh medium-reasoning coding task, official sampling temperature 1.0 / top-p .95 / top-k 20. Both already include MTP; no extra speculative multiplier is applied.
  • Cross-laptop extrapolation: take an M5 Max MTPLX reference at 614 GB/s, multiply by the laptop’s bandwidth ratio and a scenario factor of 0.8–1.0 for verification, runtime and thermal differences: speed ≈ reference × (bandwidth / 614) × 0.8…1.0. On M5 Pro (307 GB/s) the fresh-coding references 52.6–58.7 give 21.0–29.4 and the 87.6 repetitive-editing reference gives 35.0–43.8; the headline 21–44 spans both (see M5 Pro). On base M5 (153 GB/s) Qwen3.8-27B scales to only 10.5–14.6 fresh and ~22 editing, so the base M5 row uses the measured small MoE instead. Verification compute need not scale with bandwidth, so real results can fall outside these ranges.
  • Draft acceptance and fit: the model-card coding run reports acceptance by depth of .95 / .88 / .80 and a 50–53 ms verifier round on M5 Max. The estimates assume similarly favorable coding, not guaranteed acceptance on arbitrary tasks. MTPLX uses the model’s own head, not a second full draft model; its catalog reports roughly 25 GiB serving peak for this pack, so 32 GB needs a light application load and short context. Tune depth on the target Mac. Long xhigh reasoning was only 35.1–37.3 tok/s on M5 Max in the same card and is outside this faster planning scenario.
  • M5 Ultra 512 GB → GLM-5.3, 18–40 tok/s with drafting, conditional estimate. The 512 GB model has the same chip and 1.2 TB/s as the 256 GB model; its extra capacity is what lets it run GLM-5.3 (365.3 GB IQ4_XS, or a ~420 GB oQ4-class MLX build). Without drafting: ~40B active parameters × ~0.60 bytes ≈ 24 GB per token; 1,200 GB/s × 30–50% effective utilization / 24 ≈ 15–25 tok/s, which fails the gate. Cross-check: GLM-5.2 oQ4 on a 512 GB M3 Ultra measured 14.5 tok/s, or ~21 scaled to 1.2 TB/s. With drafting, apply the full B17 gain range (1.22× at 1K to 1.61× at 200 tokens) as a transfer assumption: 18.3–40.2, displayed as 18–40. A DFlash2 drafter for GLM-5.3 exists (B18), and oMLX has merged DFlash2 for GLM-5.3-Flash, but no full GLM-5.3 run on a Mac was found. The configuration ships late October. Low confidence.
  • DGX Station / GLM-5.3 IQ4_XS: 19–40 tok/s with drafting, conditional estimate. Start with 365.3 GB weights and 252 GB HBM; reserve 24–40 GB HBM for runtime, cache and verification buffers. Approximately 212–228 GB weights stay in HBM and 137–153 GB in CPU memory. Assume balanced expert placement makes the CPU-served share of active-weight traffic about 38–42%, rather than treating all 748 GB as HBM.
  • Station bandwidth calculation: use the same approximate 24 GB active-weight traffic per token as the Ultra estimate. At CPU fraction x, effective bandwidth fraction u, and non-weight overhead h, t ≈ 24×(1−x)/(7100×u) + 24×x/(396×u) + h seconds/token. With x=.38–.42, u=.50–.70 and h=.004–.008 s, this gives 15.9–25.1 tok/s without drafting. In this assumed split, CPU reads account for about 90% of modeled weight-read time, excluding other work. Resident weight fractions do not establish active traffic fractions. The 900 GB/s NVLink-C2C link does not eliminate the slower 396 GB/s CPU-memory supply; bandwidths are not added.
  • Station drafting assumption: B17 reports gains of 1.22× at 1K, 1.34× at 4K and 1.61× at 200 tokens. Transferring the full 1.22–1.61× range gives 19.5–40.3 tok/s, displayed as 19–40. This is a sensitivity scenario, not a conservative bound: acceptance, expert reuse, drafter work and backend support differ for full GLM-5.3. Drafter weights, cache and verification workspace require an additional, currently unquantified memory allowance. Without working drafting, the 16–25 baseline fails the gate and GLM-5.3-Flash in HBM (B15) is the fallback.
  • Station alternatives: MiMo-V2.6-Pro scores 46, above GLM-5.3, and is MIT-licensed, but its 1.0T / 42B-active MXFP4 checkpoint is ~566 GB. On Station 338–354 GB of it would sit in CPU memory (resident fractions do not establish actual traffic fractions). Assuming ~23 GB active-weight traffic per token and CPU traffic share x=.60–.63, the same u, h and transferred drafting gain give 15–29 tok/s; this scenario fails the gate, not a measured upper bound on the model. No measured local result was found. GLM-5.3-Flash on Station fits entirely in HBM and is measured at ~137 tok/s without speculation, 206 with MTP and 305–470 with DFlash2 (B15): the fast alternative if score 42 is enough.

Capacity-first pairings and projected speeds

Consistent selection rule: choose the highest AA-scoring model in the expanded local shortlist whose Q4-class or higher-precision weights fit with short-context serving headroom and whose displayed decode upper bound reaches 35 tok/s. Cloud ceiling models are excluded from hardware matching. SSD lookup-table offload is allowed; bulk expert weights remain in accelerator-accessible memory (Station uses its coherent CPU tier). Extremely compressed Q1/Q2 fits are excluded. Projected allocations, runtime support and drafting remain conditional.

RTX PRO: measured anchors and speed forecasts

This is a legacy no-drafter comparison, no longer the headline.   • Drafting and Spark cross-check: Spark’s 36.83–45.75 tok/s already includes MTP3, so multiplying it by 6.6 would mix memory scaling with verification and acceptance effects. The preferred dual-PRO estimate transfers B19’s complete drafting-enabled recipe; no generic speculative multiplier is applied. B13’s +30% EAGLE result on four cards is not used to scale it. These are best-effort engineering forecasts, not matched benchmark results or guaranteed bounds.

Confidence: the 165 tok/s Workstation projection remains unverified. It assumes the Server Edition B19 recipe transfers without a throughput penalty; topology, clocks, cooling, software and workload can change results. A matched Workstation run is needed. B19 is a short code-output test, while B9 spans unspecified real workloads; these are best documented setups, not a controlled cross-device comparison. 128K single-user memory budget

Common basis: 131,072 total cached tokens (prompt plus generated output), one active request, no extra prefix-cache copies or concurrent sessions. All displayed memory is decimal GB (10⁹ bytes), including converted GiB sources. Resident memory means weights plus persistent attention/recurrent/MTP state; SSD lookup tables are listed separately. Runtime allowances are planning reserves for scratch buffers, graph/workspace and allocator overhead, not measured peaks. Add roughly 6–10 GB for the OS and applications on unified-memory machines. Chunked prefill is assumed; unchunked long-prompt processing can require much more memory.

  • Qwen3.8-27B: official config has 16 full-attention layers, 4 KV heads and 256-dimensional heads. With 16-bit K/V: 131072 × 16 × 2 × 4 × 256 × 2 = 8.59 GB. Allow one full-attention MTP layer (~0.54 GB) plus 48 FP32 recurrent states (~0.15 GB) → ~9.3 GB. With 20.4 GB dynamic-Q4 weights, resident total is ~30 GB; add 4–8 GB runtime. Thus the earlier 32 GB laptop fit is for short context, not this 128K budget. Cache quantization can reduce demand if the chosen runtime supports it.
  • Flash-Next: official config has 12 full-attention layers, 2 KV heads, dimension 256, plus one MTP attention layer. Their 16-bit KV is ~3.49 GB. Add ~0.10 GB sparse-indexer keys (4× compression) and ~0.11 GB FP32 recurrent state → ~3.7 GB, rounded to 4. The selected MTPLX pack keeps ~83 GB weights resident and ~32 GB lookup tables on SSD: ~87 GB resident before 4–8 GB runtime. Different NVFP4 or all-resident packs have different weight budgets.
  • GLM-5.3: official config has 78 layers, MLA latent rank 512 and rotary key dimension 64. With one MTP layer and compressed 16-bit latent cache: 131072 × 79 × (512+64) × 2 ≈ 11.93 GB. Budget ~0.74 GB for 22 sparse-indexer key sets → ~12.7 GB, rounded to 13. IQ4_XS weights 365.3 GB + cache ≈378 GB; runtime reserve 8–16 GB. This assumes a backend that stores compressed MLA, not expanded per-head K/V.
  • GLM-5.3-Flash: official config has 11 sparse-attention layers with latent rank 512 and no rotary-key component, plus 34 recurrent layers. Budget one extra MLA layer for MTP: ~1.61 GB latent KV, ~0.10 GB 4×-pooled indexer keys and ~0.14 GB FP32 recurrent state → ~1.85 GB, rounded to 2. Depending on Q4 artifact, 156.82–199.71 GB weights + cache ≈159–202 GB; runtime reserve 8–16 GB. Backend distinction matters: expanded 64-head K/V instead of compressed MLA can consume ~95 GB for the 11 attention layers alone (~103 GB including one MTP layer), making the 128K fit much larger. The table is the compressed-cache scenario, not a claim that every oMLX/GGUF backend uses it.
  • DeepSeek V4 Flash 0731: 0731 config uses 21 attention layers compressed 4× and 20 compressed 128×, 512-dimensional shared KV, 128-dimensional index keys and a 128-token local window. Following the reference implementation’s BF16 cache layout, main compressed KV plus index keys and local windows total ~0.91 GB at 128K; reserve ~1 GB including small compressor state. About 155.1 GB Q4 weights + cache ≈156 GB; add 8–16 GB runtime. Three 0731 draft layers add small local windows, not three full context copies.
  • DeepSeek V4.1 Flash: DwarfStar Q4 main weights 294.15 GiB =315.84 GB; SSD Engram tables 188.83 GiB =202.75 GB. The model card’s packed FP4 global cache is 890 bytes/token, or 0.117 GB at 128K, plus local state. A BF16 reference-layout calculation from the shared KV/index source layers and implementation gives ~0.56 GB including local windows. Budget ~0.2–0.6 GB persistent cache; displayed resident total rounds up to ~317 GB, plus 8–16 GB runtime. These cache formats are alternative backend scenarios, not verified DwarfStar allocations. Optional vision weights add ~0.97 GB.

35 tok/s selection and ordering

Eligibility requires a measured value or range upper bound ≥35 tok/s, not a midpoint ≥35 and not a guaranteed floor. Choose the highest-scoring eligible model, then order devices by AA score and decode midpoint ascending. Forecasts are labelled E and remain conditional rather than demonstrated eligibility. The speed gate uses each row’s stated measurement/scenario; the separate 128K memory budget does not imply that speed at 128K. Halo (32–47), M5 Ultra 512 GB (18–40) and Station (19–40) qualify despite lower endpoints below 35. The two GLM-5.3 rows qualify only with an assumed DFlash2 drafter; without it both fall to 15–25 and the next pairing is GLM-5.3-Flash. MiMo-V2.6-Pro (46) fails on Station (15–29). Extra capacity buys headroom, not automatically more decode speed. Scores describe evaluated model settings, not verified local quantization quality.

Parameter counts and architecture

B = billion parameters; active = per-token backbone work, not resident memory. Dense Qwen27 uses essentially its whole language backbone; MoE models select experts, but all resident experts still consume memory. GLM-5.3: 753B / 40B active; GLM Flash: 320B / 18B; DeepSeek V4 Flash: 284B / 13B; Qwen3.8-27B: 27B dense; Qwen3.6-35B-A3B: 35B / 3B. The guide’s supported models include Qwen3-32B, Gemma 4 31B and Llama 70B; gpt-oss-120B and Qwen3.6-27B are experimental. A comparable verified dense FP4/FP8 figure and current target-model speeds were not established here. It is a specialist-stack alternative, not a drop-in CUDA/MLX equivalent. Rack GPUs (B200/B300/MI350) require server infrastructure and are outside this desk/laptop brief; DGX Station is the enterprise upper bound.

Devices not yet in the map: the Ryzen AI Max+ PRO 495 with 192 GB LPDDR5X-8533 (273 GB/s, up to 160 GB usable by the GPU, $6,399–9,249 across vendors, first systems ship November 2026) has no independent LLM measurements yet. Its 160 GB GPU limit is too tight for GLM-5.3-Flash IQ4_XS (157 GB) plus cache, so Flash-Next at Halo/Spark-class speed is the likely pairing. The used RTX 3090 (24 GB, 936 GB/s) runs Qwen3.8-27B at 40.3 tok/s at 4K without MTP and 66.4 with MTP at 8K. The Intel Arc Pro B70 (32 GB, 608 GB/s, $949 MSRP) measures only ~23 tok/s on 4-bit Qwen3.8-27B, so it would pair with Qwen3.6-35B-A3B.
