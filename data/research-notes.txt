One common model score

The shortlist now uses the Artificial Analysis Intelligence Index v4.3.2 throughout. It weights agents 30% (AA-Briefcase v1.1 15%, GDPval-AA v2.1 10%, AutomationBench-AA 5%), coding 20% (Terminal-Bench 4.0 10%, SciCode 10%), scientific reasoning 20% and general capability 30%. This is a broad independent composite, not a pure coding-agent score or a percentage success rate. No ad hoc average of vendor benchmarks is used.

Verified scores: GLM-5.3 Max 45; GLM-5.3-Flash 42; DeepSeek V4.1 Flash Max 39; Qwen3.8-27B Xhigh 34; Qwen3.8-Flash-Next reasoning 40; DeepSeek V4 Flash 0731 Max 34; Qwen3.6-35B-A3B reasoning 18. Use the stated reasoning configurations: this is a shared evaluation methodology, not an equal-compute comparison. Scores do not establish quality retention in any local quantization. The 0731 text model is distinct from its vision variant.

The AA Coding Agent Index v1.5 is more coding-specific (DeepSWE v1.1, Terminal-Bench 4.0 and SWE-Atlas-QnA), but complete public results for all seven local models could not be verified. Vendor-specific results below remain background evidence and are no longer mixed in the visible comparison.

Hardware sources and precision normalization

Arithmetic units: the main table spans GPU dense peaks and NPU/Neural Engine throughput where labeled: R9700’s dense INT4 matrix peak, NVIDIA FP4/FP8 peaks, Halo’s separate 50-TOPS INT8 NPU, and third-party estimates for Apple’s GPU Neural Accelerators. The Apple values are not rated peaks. These figures do not claim that each recommended runtime executes its quantized weights in that arithmetic; Q4 weight storage does not imply INT4 execution.

Apple compute: GPU Neural Accelerators, not the Neural Engine. Every M5-family GPU core contains a matrix unit that Apple calls a Neural Accelerator. This is the hardware that LLM runtimes such as MLX use through Metal; the 16-core Neural Engine (32-core on Ultra) is a separate, smaller block that most local-LLM runtimes do not use. Apple publishes no FLOPS figure and claims only “over 4×” the peak GPU AI compute of the matching M4 chip (M5, M5 Pro and M5 Max). Microbenchmarks on the A19, whose GPU cores are the same generation, measured about 1,024 FP16 FLOPs (FP32 accumulate) and about 1,900 INT8 ops per core per clock; BF16 was not exposed and FP8/INT4 were not measured. Scaling by core count and an assumed clock (about 1.55 GHz for M5, about 1.75 GHz for Pro/Max/Ultra) gives approximately: M5 10-core 16 TFLOPS FP16 / 30 TOPS INT8; M5 Pro 20-core 36 / 67; M5 Max 40-core 70 / 130 (matching that author’s own M5 Max extrapolation); M5 Ultra 80-core 140 / 260. The M5 figure is consistent with Apple’s 4× claim over a roughly 4 TFLOPS M4 GPU. These are dense FP16/INT8 peaks, not FP4: NVIDIA’s headline FP4 numbers are not like-for-like. The only direct M5 Max matmul measurement found, about 19.9 TFLOPS FP16, is described by its author as directional and sits well below the derived peak, so treat the table values as ceilings. Why the Macs still decode well: single-user decode streams the active weights once per token, so it is limited by memory bandwidth (614 GB/s on M5 Max, 1.2 TB/s on M5 Ultra) and by fitting the model in unified memory, not by peak compute. Compute shows up in prefill: M5 Max prefills Flash-Next at about 1,100 tok/s (B1) against about 12,000 tok/s on an RTX PRO 6000 (B9), which is the practical cost of lower matrix throughput. For reference, the Neural Engine is about 40 TOPS on 16 cores (extrapolated from M4’s 38 TOPS; not an official M5 figure).

H1 · Apple laptops. Apple technical specifications: M5 153 GB/s / 32 GB max, M5 Pro 307 / 64, full M5 Max 614 / 128. The 32-core M5 Max has only 460 GB/s. Apple’s GPU developer talk confirms neural accelerators and INT4/INT8 tensor APIs, but supplies no comparable absolute dense FP4/FP8 GPU peak. An unpublished value is not zero performance.

H2 · AMD unified-memory systems. Ryzen AI Halo specifications; Max+ 395 specifications. 128 GB, 256-bit LPDDR5X-8000 = 256 GB/s. OEM settings affect GPU allocation; faster-memory variants can differ. The separate 50-TOPS NPU is INT8 and is not the accelerator used for most of these LLM measurements.

H3 · RTX 4090. NVIDIA product specifications and Ada announcement: 24 GB, 1,008 GB/s, ~1,321 sparse FP8 TFLOPS, divided by two for ~661 dense. Quantized 4-bit weights can run without native FP4 arithmetic.

H4 · R9700. AMD specifications (32 GB / 640 GB/s), Sapphire precision brochure, p. 1: explicitly “FP8 Matrix Dense — 383 TFLOPS” and “INT4 Matrix Dense — 766 TOPS.” INT4 operations are not floating-point operations.

H5 · RTX 5090. Product page; NVIDIA Blackwell architecture whitepaper: dense / sparse FP4 1,676 / 3,352 TFLOPS. Dense FP8 is half dense FP4 (838). 32 GB, 1,792 GB/s.

H6 · RTX PRO 6000. NVIDIA PRO architecture whitepaper, pp. 45–47: Workstation FP4 2,015.2 / 4,030.4 TFLOPS and FP8 1,007.6 / 2,015.2 (dense / sparse). 96 GB ECC, 1,792 GB/s. The 300 W Max-Q has different compute; the two-card row sums full-power Workstation-class peaks and does not imply linear inference scaling.

H7 · Spark. NVIDIA specs and PNY’s explicit footnote, “Theoretical FP4 TOPS performance using sparsity feature.” 1,000 sparse TFLOPS / 2 = 500 dense FP4; FP8 is half-rate, 250. This is a theoretical normalization, not measured GEMM. Two Sparks require sharding and communication; 256 GB is not one bus at 546 GB/s.

H8 · Mac Studio. Apple specs list 96/256/512 GB M5 Ultra, 1.2 TB/s. 21 September review explicitly says 512 GB is due late October. All direct M5 Ultra measurements cited here used 256 GB. M5 Max Studio has the same stated 614 GB/s maximum as the full Max laptop; thermals and runtime can change speed.

H9 · DGX Station. Current NVIDIA datasheet, p. 3: 252 GB HBM3e at 7.1 TB/s plus 496 GB LPDDR5X at 396 GB/s; 900 GB/s NVLink-C2C, 1,600 W system / 20 A circuit. FP4 reads “20 | 15³ PFLOPS”; footnote 3 is “Without sparsity.” Thus 15 PFLOPS is the explicitly specified dense FP4, not 10 derived from a generic halving rule. FP8’s 10 PFLOPS is sparse; dense 5 PFLOPS is derived. This shipping/OEM spec supersedes the earlier 784 GB / 8 TB/s announcement. Optional RTX graphics is not counted.

How the estimates were made

Decode scope: one active request, warm model, short prompts; the remaining analytical scenarios target roughly 2–8K. Three rows remain estimates: M5 Pro, dual PRO and Station. M5 Pro spans fresh coding through favorable repetitive editing. Measured rows retain their stated contexts and drafting settings: M5 Max, Spark, Halo and R9700 include MTP; RTX 4090, RTX 5090 and the single-PRO headline do not. The separate memory comparison budgets 128K context. Station assumes conditional drafting; the dual-PRO estimate adds no speculative multiplier. Ranges are planning scenarios, not statistical confidence intervals.

M5 Pro with drafting: Qwen3.8-27B MTPLX Optimized Speed (dynamic Q4, 20.4 GB weights), native MTP head, tuned draft depth 1–3, single stream, approximately 2–8K prompt, thinking off or medium reasoning. MTPLX reports 52.6 tok/s on M5 Max at 4,061 prompt tokens / 512 output; its model card reports 58.7 tok/s on a fresh medium-reasoning coding task, official sampling temperature 1.0 / top-p .95 / top-k 20. Both already include MTP; no extra speculative multiplier is applied.

Cross-laptop extrapolation: take an M5 Max MTPLX reference at 614 GB/s, multiply by the laptop’s bandwidth ratio and a scenario factor of 0.8–1.0 for verification, runtime and thermal differences: speed ≈ reference × (bandwidth / 614) × 0.8…1.0. On M5 Pro (307 GB/s) the fresh-coding references 52.6–58.7 give 21.0–29.4 and the 87.6 repetitive-editing reference gives 35.0–43.8; the headline 21–44 spans both (see M5 Pro). On base M5 (153 GB/s) Qwen3.8-27B scales to only 10.5–14.6 fresh and ~22 editing, so the base M5 row uses the measured small MoE instead. Verification compute need not scale with bandwidth, so real results can fall outside these ranges.

Draft acceptance and fit: the model-card coding run reports acceptance by depth of .95 / .88 / .80 and a 50–53 ms verifier round on M5 Max. The estimates assume similarly favorable coding, not guaranteed acceptance on arbitrary tasks. MTPLX uses the model’s own head, not a second full draft model; its catalog reports roughly 25 GiB serving peak for this pack, so 32 GB needs a light application load and short context. Tune depth on the target Mac. Long xhigh reasoning was only 35.1–37.3 tok/s on M5 Max in the same card and is outside this faster planning scenario.

Qwen27 Q4 without drafting (reference): approximate streamed weight payload 16 GB. Use 60–80% of advertised bandwidth: tokens/s ≈ bandwidth_GBps × 0.60…0.80 / 16. Rounded: M5 6–8; M5 Pro 12–16; RTX 4090 38–50; R9700 24–32. No headline uses this formula any more: the 4090 (B10) and R9700 (B8) are now measured. Check: the 4090’s measured 46.2 tok/s at 4K sits inside its 38–50 forecast, while the RTX 5090’s 59 tok/s (B3, LM Studio on Windows) implies only ~53% bandwidth utilization, so runtime choice moves real results by more than the formula’s utilization band.

RTX PRO 6000, previous Qwen27 Q8 alternative: ~29.4 GB payload at 58–80% bandwidth gives ~35–49 tok/s. Retained as an alternative, not the capability-first headline pairing.

Why the 512 GB M5 Ultra is not listed: it has the same chip and 1.2 TB/s as the 256 GB model, so its best qualifying pairing would be the same GLM-5.3-Flash at the same speed. The only model its extra capacity unlocks is GLM-5.3 IQ4_XS: ~40B active parameters × ~0.60 bytes ≈ 24 GB of active-weight traffic per token; 1,200 GB/s / 24 ≈ 50 tok/s idealized. Use 30–50% effective utilization for MoE routing / attention / runtime → 15–25 tok/s. That fails the gate. Low confidence: forthcoming configuration, no matched test, active parameter arithmetic omits some lookup and attention traffic. The 512 GB tier buys headroom for longer contexts and parallel sessions, not a better single-user pairing.

DGX Station / GLM-5.3 IQ4_XS: 22–45 tok/s with drafting, conditional estimate. Start with 365.3 GB weights and 252 GB HBM; reserve 24–40 GB HBM for runtime, cache and verification buffers. Approximately 212–228 GB weights stay in HBM and 137–153 GB in CPU memory. Assume balanced expert placement makes the CPU-served share of active-weight traffic about 38–42%, rather than treating all 748 GB as HBM.

Station bandwidth calculation: use the same approximate 24 GB active-weight traffic per token as the Ultra estimate. At CPU fraction x, effective bandwidth fraction u, and non-weight overhead h, t ≈ 24×(1−x)/(7100×u) + 24×x/(396×u) + h seconds/token. With x=.38–.42, u=.50–.70 and h=.004–.008 s, this gives approximately 16–25 tok/s without drafting. The idealized weight-only ceiling is about 36–40 tok/s. The 900 GB/s NVLink-C2C link does not eliminate the slower 396 GB/s CPU-memory supply; bandwidths are not added.

Station drafting assumption: assume a net 1.4–1.8× gain after draft generation, verification, rejection and synchronization overhead, yielding approximately 22.28–45.12 tok/s, displayed as 22–45. This is a scenario assumption, not a measured GLM-5.3 speedup. It requires a compatible drafter or MTP implementation and an optimized split-memory backend for the exact quantization. GLM5Next MTP support in llama.cpp PR #29928 does not establish this full GLM-5.3 configuration on Station. Without working drafting, use the 16–25 baseline. CPU expert execution, poor placement, paging or low acceptance can be slower. Confidence is low; neither end is a guaranteed bound.

Station alternatives: MiMo-V2.6-Pro scores 46, above GLM-5.3, and is MIT-licensed, but its 1.0T / 42B-active MXFP4 checkpoint is ~566 GB. On Station 338–354 GB of it would sit in CPU memory (CPU traffic share x=.60–.63). With ~23 GB active-weight traffic per token and the same u and h as above, the formula gives 12–18 tok/s, or 17–32 tok/s even with the 1.4–1.8× drafting assumption; it fails the gate. No measured local result was found. GLM-5.3-Flash on Station is measured at ~137 tok/s without speculation and 305–470 with DFlash2 (single GB300, temperature 0, community post): the fast all-HBM alternative if score 42 is enough.

Capacity-first pairings and projected speeds

Consistent selection rule: choose the highest AA-scoring model in the expanded local shortlist whose Q4-class or higher-precision weights fit with short-context serving headroom and whose displayed decode upper bound reaches 35 tok/s. Cloud ceiling models are excluded from hardware matching. SSD lookup-table offload is allowed; bulk expert weights remain in accelerator-accessible memory (Station uses its coherent CPU tier). Extremely compressed Q1/Q2 fits are excluded. Projected allocations, runtime support and drafting remain conditional.

Two Sparks → Flash-Next, score 40: GLM-5.3-Flash (42) fits two Sparks (the 156.82 GB IQ4_XS artifact, or the 242 GiB NVFP4 checkpoint used in B11), but every verifiable two-Spark single-request measurement is 14.6–30.8 tok/s (B11), so it fails the 35 tok/s gate. The earlier 20–40 estimate (546 GB/s × .30–.50 × 1.3–1.5 drafting / 10.8 GB = 19.7–37.9) was too optimistic at the top. The next eligible model is Flash-Next. It fits one node, but splitting it across both with tensor parallelism (TP2) is measured faster, at 42–52 tok/s (B14) against 37–46 on one Spark (B5). A second Spark therefore buys about 25% more decode speed, plus capacity, rather than a higher-scoring model. Context Studios lists 54.4 tok/s for the same pairing (MiaAI-Lab), in line with B14. DeepSeek V4 Flash (34, ~41 tok/s in B6) remains a lower-scoring alternative.

Two RTX PRO 6000s → GLM-5.3-Flash, score 42: the 156.82 GB IQ4_XS quant leaves about 35 GB nominal aggregate headroom in 192 GB, roughly 17.6 GB per card with balanced sharding. The community NVFP4 checkpoint (~45 GiB per GPU at TP4, B13) does not fit two cards. IQ4_XS is a GGUF format, which in practice means llama.cpp, whose default multi-GPU split runs layers in sequence. The headline estimate therefore assumes single-card streaming bandwidth (see RTX PRO estimates). Short context is required. The 81.45 tok/s FP8 Flash-Next result remains in B4 as an alternative, not a GLM measurement.

Halo 128 GB → Flash-Next, score 40: the earlier 15–29 tok/s projection (256 GB/s × .40–.60 × 1.2–1.5 drafting / 8 GB) rejected this pairing. It was already inconsistent with Spark’s measured 37–46 tok/s on 273 GB/s, and B7 now measures 31.7–47.1 tok/s at 8K with UD-IQ4_XS, MTP and n-gram drafting on ROCm. The upper bound qualifies; prose and new-code workloads can stay below 35, and same-build runs varied 25–36 tok/s across days. The Flash-Next trunk (~60 GB) stays in GPU memory and the ~27 GiB PLE table in host memory, all within 128 GB. Qwen3.8-27B (34) is the fallback: ROCmFP4_FAST with near-greedy MTP reports 30.56–36.04 tok/s (B2), while AMD’s own result is 24.5 (B8).

Single PRO 6000 → Flash-Next, score 40: now measured (B9) at 81–88 tok/s without MTP and 120–173 with MTP, on vLLM with the n-gram table in host RAM rather than on SSD. The weights fit: Kubesimplify’s load used 74.75 GiB (B4). Budget a host with roughly 100 GB of free system memory.

RTX PRO: roofline plus measured latency anchor

Verified anchor: Kubesimplify reports 81.45 tok/s on two RTX PRO 6000s with Flash-Next FP8, tensor parallelism 2, one request, 1,024 input / 512 output tokens, no MTP. Four cards achieved only 64.61 tok/s. This is direct evidence against scaling decode from summed peak bandwidth alone. Single-card FP8 did not fit. A single-card NVFP4 measurement now exists (B9) and checks the forecast below. There is still no dual-card GLM-5.3-Flash measurement; four cards are measured at 63.7 tok/s (B13).

Compute and bandwidth roofs: R ≤ min(F / C, B / D), where F is FLOP/s, C FLOP/token, B bytes/s and D bytes/token. PRO/Spark ratios are 2,015/500 ≈4.0× FP4 compute and 1,792/273 ≈6.6× bandwidth. Flash-Next’s ~6B active backbone gives a lower-bound ~12 GFLOP/token; PRO’s ideal compute roof is ~168,000 tok/s, versus only 224–448 tok/s for 4–8 GB traffic/token. Arithmetic intensity is ~1.5–3 FLOP/byte versus a ~1,124 FLOP/byte hardware ridge point: strongly bandwidth-side. For dual-PRO GLM Flash, ~36 GFLOP/token and 10.8–13 GB traffic give a nominal bandwidth roof ~276–332 tok/s versus ~112,000 compute-roof tok/s. IQ4_XS is not native FP4 tensor math; that compute roof is only a generous bound, not attainable kernel throughput. Batch-one small GEMVs, dequantization and launches can dominate despite enormous peak FLOPS.

Latency model: t ≈ max(C/F_effective, D/(B×u)) + h, with effective streaming utilization u and remaining per-token overhead h. Attention traffic, routing, quantization, launch gaps, sampling, lookup staging and collectives matter. Use short-context single-stream operation with warm lookup caches; no bulk weight paging. The 81.45 tok/s FP8 anchor is 12.28 ms/token. Assuming 6–10 GB FP8 traffic and 60% aggregate streaming utilization consumes 2.79–4.65 ms in weight reads, leaving 7.63–9.49 ms residual overhead. This calibrates the order of magnitude, but one observation cannot identify traffic, utilization and overhead separately. Four cards at 15.48 ms/token reinforce the communication/launch floor.

Single PRO / Flash-Next NVFP4, superseded forecast: assume 5–7 GB/token including quantization metadata and short-context traffic, u=.50–.70 and h=4–7 ms. The central case 6/(1792×.60)+.005 = .01058 s gives 94.5 tok/s; endpoints give 67.5–125.2. B9 then measured 81–88 tok/s without MTP, inside the forecast range and ~10% below its central case. The row now shows the measurement; the forecast is kept as a calibration check on this method.

Dual PRO / GLM-5.3-Flash IQ4_XS: best ~55 tok/s; 41–70 scenario range. Assume 10.8–13 GB/token, u=.50–.65 and h=5–10 ms including communication and non-weight work. Drafting and Spark cross-check: Spark’s 36.83–45.75 tok/s already includes MTP3, so multiplying it by 6.6 would mix memory scaling with verification and acceptance effects. The measured single-PRO speed with MTP (120–173, B9) is ~3.3–3.8× the Spark MTP3 result, not 6.6×: a fixed latency floor remains as memory reads get faster. The dual-PRO estimate adds no speculative multiplier; B13’s EAGLE result (+30% on four cards) shows what a supported recipe can add, but that gain is not assumed here. These are best-effort engineering forecasts, not matched benchmark results or guaranteed bounds.

Confidence: the single-card method is now validated by one matched measurement; the dual-card estimate remains low confidence in exact throughput and runtime fit. Confidence is stronger in the conclusion that memory/runtime overhead dominates peak FLOPS. A matched two-card GLM-5.3-Flash run is still needed to narrow that range.

Lighter models that pass the speed gate

Base M5 → Qwen3.6-35B-A3B: AA score 18, with downloadable weights and an existing Apple runtime pack. This is a ~3B-active MoE, not the older 27B dense model. No verified Qwen3.8 replacement in this small-active MoE class was found. Measured (B12): 51.0–59.5 tok/s at 1K–4K with 4-bit MLX on oMLX 0.3.6, peak 19.2–20.3 GB, displayed as 51–60. The earlier roofline estimate (2.0–2.5 GB/token, u=.60–.80, h=4–8 ms → 28.4–49.2) was too pessimistic: 59.5 tok/s on 153 GB/s leaves at most 2.6 GB of traffic per token even with no fixed overhead. Even the favorable Qwen3.8-27B editing reference below scales to only ~22 tok/s on base M5, so the MoE remains the useful-speed choice.

M5 Pro → Qwen3.8-27B: use same-generation evidence rather than declaring 3.6 faster from unmatched tests. The 3.8 dynamic-Q4 pack reports 52.6–58.7 tok/s for fresh coding/short-prompt work on M5 Max, and 87.6 for rewriting a file it just wrote. Scale each by 307/614 and .8–1.0: ~21–29 for fresh coding, ~35–44 for repetitive editing. The headline 21–44 spans those workloads and meets the user's upper-bound rule, not a general 35 tok/s floor. It is an estimate on M5 Pro; the 87.6 source is a favorable MTPLX 2.10.0 result, not a matched cross-device measurement. The 3.6/3.8 configs share core dimensions, but quantization payload, learned draft acceptance and kernels still affect speed. The older 3.6-27B recommendation is removed. Independent cross-check: a 4-bit Qwen3.8-27B MTPLX pack reports a 2.33× MTP multiplier verified on M5 Pro (best depth 3, temperature 0.6; no absolute speeds published). Applied to the ~17–18 tok/s that oMLX community runs report for plain Qwen3.5-27B on M5 Pro, that gives roughly 40–42 tok/s, consistent with the upper half of the range. No direct M5 Pro measurement of this pack was found, so the row stays an estimate. For a faster lower-score option, oMLX reports 98–102 tok/s for the Qwen3.6-35B-A3B MTPLX pack on M5 Pro.

128K single-user memory budget

Common basis: 131,072 total cached tokens (prompt plus generated output), one active request, no extra prefix-cache copies or concurrent sessions. All displayed memory is decimal GB (10⁹ bytes), including converted GiB sources. Resident memory means weights plus persistent attention/recurrent/MTP state; SSD lookup tables are listed separately. Runtime allowances are planning reserves for scratch buffers, graph/workspace and allocator overhead, not measured peaks. Add roughly 6–10 GB for the OS and applications on unified-memory machines. Chunked prefill is assumed; unchunked long-prompt processing can require much more memory.

Qwen3.8-27B: official config has 16 full-attention layers, 4 KV heads and 256-dimensional heads. With 16-bit K/V: 131072 × 16 × 2 × 4 × 256 × 2 = 8.59 GB. Allow one full-attention MTP layer (~0.54 GB) plus 48 FP32 recurrent states (~0.15 GB) → ~9.3 GB. With 20.4 GB dynamic-Q4 weights, resident total is ~30 GB; add 4–8 GB runtime. Thus the earlier 32 GB laptop fit is for short context, not this 128K budget. Cache quantization can reduce demand if the chosen runtime supports it.

Flash-Next: official config has 12 full-attention layers, 2 KV heads, dimension 256, plus one MTP attention layer. Their 16-bit KV is ~3.49 GB. Add ~0.10 GB sparse-indexer keys (4× compression) and ~0.11 GB FP32 recurrent state → ~3.7 GB, rounded to 4. The selected MTPLX pack keeps ~83 GB weights resident and ~32 GB lookup tables on SSD: ~87 GB resident before 4–8 GB runtime. Different NVFP4 or all-resident packs have different weight budgets.

GLM-5.3: official config has 78 layers, MLA latent rank 512 and rotary key dimension 64. With one MTP layer and compressed 16-bit latent cache: 131072 × 79 × (512+64) × 2 ≈ 11.93 GB. Budget ~0.74 GB for 22 sparse-indexer key sets → ~12.7 GB, rounded to 13. IQ4_XS weights 365.3 GB + cache ≈378 GB; runtime reserve 8–16 GB. This assumes a backend that stores compressed MLA, not expanded per-head K/V.

GLM-5.3-Flash: official config has 11 sparse-attention layers with latent rank 512 and no rotary-key component, plus 34 recurrent layers. Budget one extra MLA layer for MTP: ~1.61 GB latent KV, ~0.10 GB 4×-pooled indexer keys and ~0.14 GB FP32 recurrent state → ~1.85 GB, rounded to 2. Depending on Q4 artifact, 156.82–199.71 GB weights + cache ≈159–202 GB; runtime reserve 8–16 GB. Backend distinction matters: expanded 64-head K/V instead of compressed MLA can consume ~95 GB for the 11 attention layers alone (~103 GB including one MTP layer), making the 128K fit much larger. The table is the compressed-cache scenario, not a claim that every oMLX/GGUF backend uses it.

DeepSeek V4 Flash 0731: 0731 config uses 21 attention layers compressed 4× and 20 compressed 128×, 512-dimensional shared KV, 128-dimensional index keys and a 128-token local window. Following the reference implementation’s BF16 cache layout, main compressed KV plus index keys and local windows total ~0.91 GB at 128K; reserve ~1 GB including small compressor state. About 155.1 GB Q4 weights + cache ≈156 GB; add 8–16 GB runtime. Three 0731 draft layers add small local windows, not three full context copies.

DeepSeek V4.1 Flash: DwarfStar Q4 main weights 294.15 GiB =315.84 GB; SSD Engram tables 188.83 GiB =202.75 GB. The model card’s packed FP4 global cache is 890 bytes/token, or 0.117 GB at 128K, plus local state. A BF16 reference-layout calculation from the shared KV/index source layers and implementation gives ~0.56 GB including local windows. Budget ~0.2–0.6 GB persistent cache; displayed resident total rounds up to ~317 GB, plus 8–16 GB runtime. These cache formats are alternative backend scenarios, not verified DwarfStar allocations. Optional vision weights add ~0.97 GB.

35 tok/s selection and ordering

Eligibility requires a measured value or range upper bound ≥35 tok/s, not a midpoint ≥35 and not a guaranteed floor. Choose the highest-scoring eligible model, then order devices by AA score and decode midpoint ascending. The speed gate uses each row’s stated short-context measurement/scenario; the separate 128K memory budget does not imply that speed at 128K. Station (22–45), Halo (32–47) and Ultra 256 (28–41) qualify despite lower endpoints below 35. Dual Spark switches from GLM-5.3-Flash (14.6–30.8 measured, fails) to Flash-Next. Station keeps GLM-5.3 because the higher-scoring MiMo-V2.6-Pro (46) fails the gate on the same split-memory formula (17–32 with drafting). Extra capacity buys headroom, not automatically more decode speed. Scores describe evaluated model settings, not verified local quantization quality.

Parameter counts and architecture

B = billion parameters; active = per-token backbone work, not resident memory. Dense Qwen27 uses essentially its whole language backbone; MoE models select experts, but all resident experts still consume memory. GLM-5.3: 753B / 40B active; GLM Flash: 320B / 18B; DeepSeek V4 Flash: 284B / 13B; Qwen3.8-27B: 27B dense; Qwen3.6-35B-A3B: 35B / 3B. Counts follow vendor conventions and do not always separately itemize vision or draft heads. Flash-Next’s ~180B sum is 125B backbone +51B lookup embeddings +4B MTP, with 6B active backbone. DeepSeek V4.1’s ~763B full checkpoint includes a 552B backbone and 196B Engram tables plus auxiliary components; 16B active is decode (prefill: 8B). Sparse table lookups and draft verification are additional work, so these active counts alone are not FLOP or bandwidth budgets. The cloud models’ parameter counts and Dense/MoE architecture are undisclosed.

Model storage, fit and selection notes

Model size is not serving memory. GB = 10⁹ bytes; GiB = 2³⁰ bytes. Vendor installed capacities are retained as advertised. Quantization sources use their displayed units. Plan for runtime allocations, KV cache, vision, MTP and the operating system; native 1M context does not promise a 1M deployment on each device.

Qwen3.8-27B. Official model card; concrete 16.0/20.4 GB Q4 and 29.4 GB Q8 packs. Its 61.7 SWE-bench Pro used Qwen’s corrected tasks, Claude Code, temperature 1 / top-p .95 and 256K context. It also reports 73.0 Terminal-Bench 2.1 (Terminus). A 24 GB GPU can fit compact Q4 at modest context; the high-quality dynamic Q4 plus long KV may not. Base M5 recommendation assumes the 32 GB configuration, not 16 GB.

Flash-Next. Official card: 125B backbone + 51B n-gram embeddings + 4B MTP (~180B total); 6B active backbone. Do not size this as only 125B. Q4_K_XL shards total ~111.4 GB, separate MTP Q8 4.14 GB, vision ~0.9 GB. 128 GB all-resident is marginal; the selected M5 Max and Spark recipes explicitly offload lookup tables. MTPLX uses dynamic Q4 with sparse-attention projections at Q8. GGUF, NVFP4 and oQ4e are not interchangeable.

96 GB alternatives. Flash-Next UD-IQ1_S is ~67.55 GiB (effective 3.28 bits/weight), so it fits a PRO 6000 with serving headroom; its low-bit experts have unverified agentic quality here. The Spark measurement for this quant is not a PRO 6000 measurement. A PRO 6000 DeepSeek V4 Flash ds4.c result reports 46.9 tok/s, using more compressed weights than the dual-Spark reference. The main map instead projects a higher-precision Flash-Next fit with SSD lookup-table staging; Qwen27 Q8 remains the simpler high-fidelity fallback.

DeepSeek V4 Flash. Official original card; 0731 Q4_K_XL shards ~155.1 GB. The 54.4 DeepSWE figure comes from the Qwen Flash-Next comparison explicitly labeling 0731. Original-release benchmarks (e.g. SWE-bench Verified 79.0 / Pro 52.6 and Terminal-Bench 2.0 56.9) are different versions/protocols and not substituted for newer scores.

GLM-5.3-Flash. Official card and quantization guide: IQ4_XS 156.82 GB, Q4_K_XL 199.71 GB; the measured Mac uses a separate mixed-4/8 MLX artifact. 84.3 Terminal-Bench 2.1 uses Claude Code 2.1.207, while 63.4 DeepSWE uses mini-SWE at 400K / six hours. 128 GB can squeeze lower-bit variants, but this guide prefers useful precision and headroom. Token-level agreement percentages are not task success rates.

GLM-5.3. Official card; actual quantization table. IQ4_XS 365.3 GB leaves much more headroom on 512 GB than Q4_K_XL 467.3 GB. ~753B total / 40B active from AA (some guides use 744B backbone). Broader capability and alternative hardware

Artificial Analysis’s current open-weight index ranks MiMo-V2.6-Pro (46), GLM-5.3 (45), Kimi K3 (44), then GLM-5.3-Flash (42) in broad intelligence. Considered but not shortlisted: MiMo-V2.6-Pro (1.0T / 42B active, ~566 GB MXFP4) fits only Station and fails the gate there (see Station alternatives); Kimi K3 (2.8T / 104B active) fits none of these devices at Q4; MiMo-V2.6-Flash (38; 309B / 15B active; MIT; ~166–178 GB at 4-bit, 59.4 tok/s reported on M3 Ultra 256 GB) scores below both GLM-5.3-Flash and Flash-Next, so it wins no row. Scores shown are v4.3.2 (not the earlier index that gave Qwen27 ~52). AA’s hosted-provider tokens/sec is deliberately not used as local hardware speed. Qwen3.8-Max and proprietary frontier models are not assumed to have downloadable weights. “Open weight” does not mean every license is identical: Flash-Next uses Qwen Community terms; GLM-5.3 has its own license; Flash variants from DeepSeek and GLM-5.3-Flash list MIT.

Tenstorrent QuietBox 2: four Blackhole chips on two p300c cards; 128 GB accelerator GDDR6 (32/chip), 1,024 GB/s per card / 2,048 GB/s aggregate; separate 256 GB host DDR5. The guide’s supported models include Qwen3-32B, Gemma 4 31B and Llama 70B; gpt-oss-120B and Qwen3.6-27B are experimental. A comparable verified dense FP4/FP8 figure and current target-model speeds were not established here. It is a specialist-stack alternative, not a drop-in CUDA/MLX equivalent. Rack GPUs (B200/B300/MI350) require server infrastructure and are outside this desk/laptop brief; DGX Station is the enterprise upper bound.

Devices not yet in the map: the Ryzen AI Max+ PRO 495 with 192 GB LPDDR5X-8533 (273 GB/s, up to 160 GB usable by the GPU, $6,399–9,249 across vendors, first systems ship November 2026) has no independent LLM measurements yet. Its 160 GB GPU limit is too tight for GLM-5.3-Flash IQ4_XS (157 GB) plus cache, so Flash-Next at Halo/Spark-class speed is the likely pairing. The used RTX 3090 (24 GB, 936 GB/s) runs Qwen3.8-27B at 40.3 tok/s at 4K without MTP and 66.4 with MTP at 8K. The Intel Arc Pro B70 (32 GB, 608 GB/s, $949 MSRP) measures only ~23 tok/s on 4-bit Qwen3.8-27B, so it would pair with Qwen3.6-35B-A3B.

Purchase takeaway: For one practical machine today, the M5 Ultra 256 GB has strong measured large-model options; M5 Max 128 GB is the portable alternative; Spark is attractive for CUDA development; a second Spark speeds the same Flash-Next pairing to 42–52 tok/s rather than unlocking a higher-scoring model. Halo now runs the same score-40 model as Spark at similar measured speed for less money. A single RTX PRO 6000 is the fastest measured score-40 setup if the host has ample RAM. An RTX 5090 is a responsive compact-model accelerator, not a replacement for a 256 GB memory pool. The best end-to-end agent is the one that completes the task correctly with fewer retries—not necessarily the highest decode number.
